# Архитектура dotfiles

Целевая архитектура для нескольких рабочих станций на macOS и NixOS.
На каждой машине один управляемый пользователь; логины могут отличаться.
NixOS поддерживается на `aarch64-linux` и `x86_64-linux`.

Документ описывает будущую реализацию. Примеры структуры, опций и команды
`dotfiles` ниже — проектируемый интерфейс, а не уже существующие возможности
репозитория. Этот документ заменяет предыдущие решения из `arch.html`.

## 1. Основное решение

Машина явно перечисляет нужные ей программы и системные возможности в одном
списке `modules`. Каждый модуль имеет одну точку подключения и объединяет
нужные ему пакеты, системную интеграцию и файлы пользователя. Любая из этих
частей может отсутствовать. Конфиги остаются в родном формате программы и
по умолчанию редактируются прямо в рабочей копии Git-репозитория.

- NixOS управляет Linux-системой, nix-darwin — доступными ему настройками macOS.
- Home Manager встроен в обе системы и управляет подключением пользовательских
  файлов. Отдельного списка приложений для Home Manager нет.
- `modules/<имя>/` содержит всю логику программы или системной возможности,
  включая её конфиги и различия между ОС и машинами.
- `hosts/<машина>/` выбирает модули, варианты их настроек и описывает железо.
- Теги, группы приложений `work/personal` и общий автоматически включённый
  набор программ не нужны. Списки у машин независимы.
- Одна команда `dotfiles apply` применяет выбранную машину. Изменение обычного
  конфига чаще всего вообще не требует применения Nix.

Встраивание Home Manager поддерживается штатно и на
[NixOS](https://nix-community.github.io/home-manager/installation/nixos.html),
и в [nix-darwin](https://nix-community.github.io/home-manager/installation/nix-darwin.html).

```text
Описание машины: платформа + пользователь + список modules
                         │
                     make-host
                         │
              modules/<имя>/default.nix
                  ├── пакеты и настройки ОС, если нужны
                  └── Home Manager, если нужен → подключение конфигов
                                          │
                                обычные файлы в Git
                                          ↕
                                редактор / ИИ / GUI
```

## 2. Структура репозитория

```text
flake.nix                       # зависимости и именованный перечень машин
flake.lock
arch.md
bin/
└── dotfiles                    # единый CLI
lib/
└── make-host.nix               # сборка машины и интеграция Home Manager
shared/
├── home.nix                    # основа Home Manager и общие механизмы
├── nixos.nix                   # общая основа NixOS
└── darwin.nix                  # общая основа nix-darwin
hosts/
├── personal-mac/
│   ├── default.nix             # данные машины и единый список модулей
│   └── machine.nix             # индивидуальные системные настройки
└── personal-nixos/
    ├── default.nix
    ├── machine.nix
    └── hardware-configuration.nix
modules/
├── apple-silicon-support/
│   ├── default.nix             # общая поддержка Apple Silicon в NixOS
│   ├── modules/                # ядро, загрузка, звук, firmware
│   └── packages/               # пакеты и overlay этой поддержки
├── git/
│   ├── default.nix
│   └── files/
│       ├── common.gitconfig
│       └── variants/
│           ├── personal/config
│           └── work/config
├── ssh/
│   ├── default.nix             # единственная внешняя точка подключения
│   ├── home.nix
│   ├── nixos.nix
│   ├── darwin.nix
│   └── files/config
├── ghostty/
│   ├── default.nix
│   └── files/                  # конфиг и темы
├── hyprland/
│   ├── default.nix
│   ├── nixos.nix
│   ├── home.nix
│   └── files/
│       ├── common.lua
│       └── hosts/
│           └── personal-nixos/ # входной конфиг и мониторы этой машины
├── example-tool/               # пример программы со своим Nix-пакетом
│   ├── default.nix             # подключение пакета и настроек
│   ├── package.nix             # получение или сборка самой программы
│   └── files/                  # обычные пользовательские конфиги
└── nvim/
    └── default.nix             # пакет, инструменты и внешний репозиторий
```

Файлы `home.nix`, `nixos.nix`, `darwin.nix`, `machine.nix` создаются только
при необходимости. Маленькой программе достаточно `default.nix` и её файлов.
Шрифты, Bluetooth и другие системные возможности также могут быть модулями.

В `shared/` находятся базовые параметры Nix и Home Manager, интеграция ОС и
общие механизмы подключения файлов. Настройки SSH, Git или Hyprland туда
не переносятся. `home/default.nix` как второй каталог приложений больше не нужен.

## 3. Описание машины

Каждый каталог в `hosts/` описывает конкретный компьютер. Пока их два:
`personal-mac` и `personal-nixos`. Это имена машин, а не шаблоны для всех Mac
или NixOS-компьютеров. При появлении нового компьютера у него будет своё имя
и описание. Тип железа задаётся внутри описания и не определяет имя хоста.

`hosts/<имя>/default.nix` — обычный набор данных Nix, который читает `make-host`.
Это не системный модуль. Например:

```nix
# hosts/personal-mac/default.nix
{
  system = "aarch64-darwin";
  user = "stounfo";

  modules = [
    ./machine.nix
    ../../modules/git
    ../../modules/ssh
    ../../modules/nvim
    ../../modules/ghostty
  ];

  settings.git.variant = "personal";
}
```

Добавить программу или системную возможность — добавить её модуль в `modules`.
Убрать — удалить из `modules` и применить конфигурацию. Для запрещённой на
работе программы достаточно отсутствия в списке рабочей машины. Отдельной
системы запретов нет.

`./machine.nix` также подключается через этот список. Он хранит индивидуальные
настройки компьютера; переиспользуемые модули лежат в общем `modules/`.
Их расположение отличается, но механизм подключения одинаковый.

Повторение названий программ в списках разных машин допустимо: это независимый
выбор состава. Установка и настройки каждой программы описываются один раз.

`settings` содержит только входные параметры модулей: например, выбор варианта
Git или каталога конфигурации. Модуль не проверяет имена вроде `personal-mac` и
не хранит таблицу всех компьютеров. Варианты `personal` и `work` в примере —
варианты конфига Git, а не группы устанавливаемых программ.

`make-host.nix` — наша вспомогательная функция, а не встроенный механизм Nix.
Имя выбрано ради читаемости; обязательного имени `mk-host` нет. Она получает
имя машины из реестра во flake и один раз вычисляет:

- ОС из `system`: `darwin` или `nixos`;
- домашний каталог из ОС и `user`, с возможностью явно указать нестандартный;
- `dotfilesDir = "${homeDirectory}/dotfiles"` — путь к рабочей копии;
- `reposDir = "${homeDirectory}/.local/share/dotfiles/repos"` — внешние конфиги.

Эти значения передаются системным модулям как `host` через `specialArgs`,
а Home Manager — через `home-manager.extraSpecialArgs`. `make-host` также
подключает Home Manager, соответствующий `shared/` и весь список `host.modules`.
Он не разделяет выбранные модули по назначению: программы, оборудование и
локальные настройки подключаются одинаково. Имя пользователя в модулях
не хардкодится.

Платформа задаётся через `nixpkgs.hostPlatform` из одного `host.system`.
Home Manager использует общий с системой набор пакетов и одного
`home-manager.users.${host.user}`. Фабрика настраивает пользователя NixOS
или связывается с существующей учётной записью macOS. Во flake результаты
попадают в `nixosConfigurations.<имя>` и `darwinConfigurations.<имя>`
соответственно; перечень машин также существует в одном месте.

В интеграции Home Manager задаются `useGlobalPkgs = true` и
`useUserPackages = true`. Управляемые пакеты устанавливаются через системную
опцию `users.users.<имя>.packages`; личный профиль для ручных `nix profile`
остаётся отдельным. Этот механизм общий для NixOS и nix-darwin:
[интеграция Home Manager](https://github.com/nix-community/home-manager/blob/master/nixos/common.nix).

| Машина | `system` | Особенности |
| --- | --- | --- |
| `personal-mac` | `aarch64-darwin` | nix-darwin |
| `personal-nixos` | `aarch64-linux` | NixOS и модуль Apple Silicon |

Будущая машина на x86-64 получит `system = "x86_64-linux"` и собственную
конфигурацию оборудования. UUID дисков, разметка и индивидуальные настройки
загрузчика и устройств остаются в `hosts/<имя>/`. Значения `system.stateVersion`
и `home.stateVersion` сохраняются при миграции существующих машин; обновление
зависимостей само их не повышает.

### Общая поддержка Apple Silicon

Текущий каталог `apple-silicon-support/` в целевой структуре размещается целиком
в `modules/apple-silicon-support/`, сохраняя свои внутренние `modules/` и
`packages/`. Это переиспользуемый системный модуль. Его `default.nix` подключает
реализацию и включает `hardware.asahi.enable`; ядро, драйверы, overlay и общая
интеграция описываются здесь один раз.

`personal-nixos` выбирает эту поддержку в том же списке, что и программы:

```nix
# hosts/personal-nixos/default.nix
{
  system = "aarch64-linux";
  user = "stounfo";

  modules = [
    ./machine.nix
    ../../modules/apple-silicon-support
    ../../modules/git
    ../../modules/ssh
    ../../modules/nvim
    ../../modules/ghostty
    ../../modules/hyprland
  ];

  settings.git.variant = "personal";
}
```

`machine.nix` подключает локальный `hardware-configuration.nix` и задаёт
индивидуальные параметры, например расположение firmware этой машины.
Повторять в нём включение общей поддержки не требуется.

Если она понадобится ещё одному компьютеру, его список `modules` подключает
тот же `../../modules/apple-silicon-support`. Код поддержки не копируется,
списка имён компьютеров внутри неё нет. Модуль выбирается только для нужных
NixOS-машин: Apple Silicon в macOS и любой другой ARM-компьютер сами по себе
не являются поводом включать поддержку Asahi.

## 4. Один модуль — одна точка подключения

`modules/<имя>/default.nix` является системным модулем. Он может подключить
внутреннюю часть для ОС и пользовательскую часть через Home Manager.
Это общий контракт для всех модулей: Git в основном настраивает пользовательское
окружение, SSH — систему и пользователя, Apple Silicon Support — только систему.
Пользовательская часть и установка отдельного приложения необязательны;
пустые `home.nix` или фиктивные пакеты для единообразия не создаются.

```nix
# modules/ssh/default.nix
{ lib, host, ... }:
{
  imports =
    lib.optionals (host.os == "nixos") [ ./nixos.nix ]
    ++ lib.optionals (host.os == "darwin") [ ./darwin.nix ];

  home-manager.users.${host.user}.imports = [ ./home.nix ];
}
```

Машина подключает только `../../modules/ssh`. SSH-клиент, агент,
пользовательский конфиг и различия macOS/NixOS остаются в этой директории.
Включение клиента не подразумевает включения SSH-сервера.

У программы только для NixOS условие охватывает всю программу:

```nix
# modules/hyprland/default.nix
{ host, ... }:
if host.os == "nixos" then {
  imports = [ ./nixos.nix ];
  home-manager.users.${host.user}.imports = [ ./home.nix ];
} else { }
```

Поддержка архитектуры проверяется внутри той же программы, если она отличается
между ARM и x86-64. Неподдерживаемый вариант ничего не добавляет, включая
конфиги. Для обычной работы достаточно корректного явного списка машины.
Неизвестные системные опции другой ОС не должны попадать в её модульный граф.

Способ установки выбирает модуль: предпочтение отдаётся подходящему Nix-пакету
и для CLI, и для GUI. На macOS при необходимости модуль использует Homebrew cask
через nix-darwin. Homebrew в этом случае — внутренняя деталь установки;
пользователь не запускает `brew install`, `brew upgrade` или `brew uninstall`.
Списка casks, вручную продублированного во flake, нет.

Запись программы в `modules` обозначает её модуль, а не атрибут пакета в nixpkgs.
Разные имена пакетов, способы установки и пути конфигов для разных платформ
разрешаются внутри этого модуля. Например, обе машины выбирают
`../../modules/ghostty`, а сам модуль выбирает пакет:

```nix
# modules/ghostty/default.nix
{ host, ... }:
{
  home-manager.users.${host.user} = { config, pkgs, ... }: {
    home.packages = [
      (if host.os == "darwin" then pkgs.ghostty-bin else pkgs.ghostty)
    ];

    xdg.configFile."ghostty".source = config.lib.file.mkOutOfStoreSymlink
      "${host.dotfilesDir}/modules/ghostty/files";
  };
}
```

Такие варианты есть в nixpkgs:
[`ghostty` для Linux](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/gh/ghostty/package.nix)
и [`ghostty-bin` для Darwin](https://github.com/NixOS/nixpkgs/blob/master/pkgs/by-name/gh/ghostty-bin/package.nix).
При реализации их доступность проверяется в закреплённом `flake.lock`.
Если способ установки изменится, меняется только модуль Ghostty. Конфиги и
темы остаются общими там, где сама программа поддерживает общий формат.

Если системный модуль уже устанавливает пакет, пользовательская часть второй
раз его не устанавливает. Системные зависимости программы остаются внутри её
модуля. Самостоятельные приложения не должны незаметно включаться друг через
друга; небольшие необходимые инструменты, например компилятор для Neovim,
могут быть зависимостями его модуля.

### Программы, которых нет в nixpkgs

Модуль и пакет решают разные задачи. Пакет описывает, откуда взять программу
и как подготовить её для запуска. Модуль выбирает пакет, устанавливает его
в нужное окружение и подключает конфиги и системную интеграцию.

Если подходящего пакета нет в nixpkgs, его определение хранится рядом с модулем:
`modules/<программа>/package.nix`. Этот файл возвращает обычный Nix-пакет;
`default.nix` получает его через `pkgs.callPackage`:

```nix
# modules/example-tool/default.nix
{ host, ... }:
{
  home-manager.users.${host.user} = { pkgs, ... }: {
    home.packages = [ (pkgs.callPackage ./package.nix { }) ];
  };
}
```

Хост добавляет только `../../modules/example-tool` в свой список `modules`.
Регистрация второго имени пакета во flake или в отдельном списке не требуется.
Если пакетов несколько, вместо одного файла появляется внутренний `packages/`,
как у Apple Silicon Support. Конфиги остаются в `files/` того же модуля.

Определение пакета может собирать исходники, упаковывать готовый релиз
производителя или устанавливать собственный скрипт. Для этого используются
обычные средства Nix: подходящий сборщик, `stdenv.mkDerivation`, fetchers или
`writeShellApplication`. Они описаны в
[руководстве nixpkgs](https://nixos.org/manual/nixpkgs/stable/).
Если для macOS и Linux нужны разные определения пакета или архивы под ARM
и x86-64, выбор остаётся внутри директории программы.

Для собственных пакетов действуют следующие правила:

- Версия или commit и хеш загружаемого исходника/архива фиксируются в
  определении пакета. Если источник оформлен как flake input, его ревизию
  фиксирует `flake.lock`. Собственный `package.nix` не обязан становиться input.
- Указывается фактически поддерживаемый набор ОС и архитектур. Наличие своего
  пакета не делает программу автоматически доступной на всех машинах.
- Сборка подготавливает результат в Nix store. Запись конфигов в домашний
  каталог и включение сервисов остаются работой модуля при применении.
- Установка и отключение работают так же, как у пакета из nixpkgs. Отдельные
  команды скачивания при каждой активации и собственный удаляющий скрипт
  для обычного пакета не нужны.
- Новая версия собственного пакета задаётся изменением его определения и
  применяется через `dotfiles apply`. Обновление `flake.lock` само не меняет
  захардкоженные версию и хеш в `package.nix`.

Для одного локального пакета overlay не требуется. Если понадобится подменять
пакет и в зависимостях других программ, overlay также хранится рядом с его
модулем и подключается из `default.nix`. При появлении подходящего пакета
в nixpkgs можно заменить внутреннее определение, сохранив подключение хостов.

Такой пакет описывает исполняемую программу. Редактируемый внешний конфиг,
например `stounfo/nvim`, по-прежнему остаётся рабочим Git-репозиторием по
правилам раздела 8 и не превращается в неизменяемый пакет.

## 5. Обычные конфиги и немедленные изменения

Основной режим — ссылка из домашнего каталога на редактируемые файлы в
`~/dotfiles/modules/<программа>/files/`. Исходники не копируются при каждом
применении и не перегенерируются из Nix.

Home Manager предоставляет `mkOutOfStoreSymlink` для ссылки за пределы
Nix store. В модуле Git это выглядит так:

```nix
# modules/git/default.nix
{ host, ... }:
{
  home-manager.users.${host.user} = { config, pkgs, ... }: {
    home.packages = [ pkgs.git ];

    xdg.configFile."git".source = config.lib.file.mkOutOfStoreSymlink
      "${host.dotfilesDir}/modules/git/files/variants/${host.settings.git.variant}";
  };
}
```

Здесь передаётся абсолютный путь-строка к рабочей копии. `./files` внутри flake
может обозначать уже скопированный в store исходник и для этого режима
не подходит. Механизм ссылки описан в
[исходниках Home Manager](https://github.com/nix-community/home-manager/blob/master/modules/files.nix).

`~/dotfiles` — согласованное постоянное расположение репозитория. Начальная
команда создаёт или использует эту рабочую копию. Её нельзя удалять после
установки. Вводить произвольное расположение пока не нужно: оно потребовало бы
также обновить пути в обычных include-файлах. Пути Nix-модулей вычисляются
из описания машины, а не текущей директории или окружения `sudo`.

Сохранение исходного файла сразу меняет то, что читает приложение. Когда
приложение прочитает его заново — при следующем запуске, через reload или
автоматически — зависит от приложения. Пересборка Nix для этого не нужна.

### Запись через редактор, ИИ и GUI

Если программа сохраняет конфиг через временный файл и `rename`, ссылка на
отдельный файл может быть заменена обычным файлом. Поэтому для конфигурационных
каталогов, в которые приложение пишет, подключается каталог целиком,
с обычными записываемыми файлами внутри. `recursive = true` для таких каталогов
не используется.

Это покрывает редакторы, которые атомарно заменяют файлы внутри каталога.
Поведение конкретного GUI, особенно если он заменяет сам каталог, проверяется
при его подключении. Универсальной гарантии для любого GUI нет.

Для одиночного файла, например `~/.ssh/config`, редактируется настоящий
исходник в репозитории. ИИ получает путь к этому исходнику. Приложения,
которые сами пишут в такой файл, требуют отдельного решения в своём модуле.
Весь `~/.ssh` ссылкой в Git не заменяется: ключи и изменяемое состояние
живут отдельно.

Один путь имеет одного владельца: либо наш файл, либо генератор Home Manager.
Например, нельзя одновременно генерировать Git-конфиг через `programs.git`
и подключать по тому же пути редактируемый файл. Готовые Nix-модули можно
использовать для интеграции, если они не перехватывают этот файл.

## 6. Различия конфигов между машинами

Приоритет у возможностей самой программы: `include`, дополнительные файлы,
локальные настройки. Общая часть хранится один раз; различия остаются
небольшими обычными файлами в директории программы.

Для Git выбран каталог `~/.config/git`, чтобы его содержимое можно было
редактировать, в том числе атомарной записью. Это штатный глобальный путь Git.
Например, `modules/git/files/variants/work/config`:

```gitconfig
[include]
    path = ~/dotfiles/modules/git/files/common.gitconfig

[user]
    name = Oleg Levantin
    email = oleg@company.example
```

Общие aliases, pager и остальные настройки находятся в `common.gitconfig`.
Рабочие имя и email задаются только в файле варианта; их нет второй раз в Nix.
Для отдельной машины можно добавить собственный вариант. Подстановка `~`
в include поддерживается Git; здесь используется согласованный путь репозитория.

При переходе старый `~/.gitconfig` нужно перенести с сохранением содержимого,
чтобы он не переопределял новый глобальный конфиг. Порядок чтения файлов и
механизм include описаны в [документации Git](https://git-scm.com/docs/git-config).

### Когда всё-таки нужен шаблон

Если программа не умеет подключать дополнительные файлы, модуль может хранить
`files/config.tmpl` в её родном синтаксисе и подставлять несколько значений.
Результат генерируется при применении; исходником остаётся шаблон. Генерация
не должна превращаться в описание всего конфига Nix-атрибутами.

Для такого файла ИИ редактирует шаблон и его параметры, затем запускается
`dotfiles apply`. Ручные изменения сгенерированного результата автоматически
обратно в шаблон не переносятся.

Поэтому шаблон не является основным режимом для конфигов, которые пользователь
или GUI постоянно меняет после установки. Если нет include, а такой процесс
нужен, предпочтителен обычный готовый файл варианта. Небольшое дублирование
в этом исключении лучше, чем необходимость постоянно восстанавливать изменения.
Двусторонний синхронизатор шаблонов не проектируется.

## 7. Hyprland и настройка мониторов через GUI

Каталог `~/.config/hypr` подключается целиком к каталогу текущей машины:

```text
~/.config/hypr
  → ~/dotfiles/modules/hyprland/files/hosts/personal-nixos/
      ├── hyprland.lua
      ├── monitors.lua
      └── workspaces.lua
```

По умолчанию модуль выбирает `files/hosts/${host.name}`; путь можно переопределить
через `settings.hyprland`. Это правило пути, а не таблица имён машин в модуле.
Входной `hyprland.lua` подключает общий
`~/dotfiles/modules/hyprland/files/common.lua` и локальные файлы мониторов
и рабочих пространств. Повторяться между машинами могут короткие строки
подключения; бинды, оформление и остальные общие настройки не копируются.

Файлы мониторов и рабочих пространств — обычные файлы внутри записываемого
каталога. GUI меняет их, и изменение сразу оказывается в рабочей копии dotfiles.
Оно видно в `git diff`, переживает `dotfiles apply` и после commit/push
может быть восстановлено на этой машине. Настройки мониторов другого хоста
не затрагиваются. Новые созданные GUI файлы нужно также добавить в Git.

Например, `nwg-displays` умеет сохранять расположение мониторов и привязки
рабочих пространств. Формат выбирается по закреплённым версиям Hyprland и GUI:
для Lua используются `.lua` и `require`, для прежнего hyprlang — `.conf` и
`source`. Поддержка описана в
[документации nwg-displays](https://github.com/nwg-piotr/nwg-displays#hyprland).
Пример выше не утверждает, что текущий `flake.lock` уже использует Lua.

При реализации проверяется именно установленная пара версий. GUI должен
сохранять подключённые файлы, а не только менять текущую сессию. Если выбранный
GUI работает только с целым конфигом, он получает отдельный файл этой машины;
общие настройки из него по возможности выносятся штатными include.

Первичная раскладка мониторов хранится в файлах машины. Nix не записывает её
повторно при каждом применении и не генерирует параллельные правила мониторов.
Сам GUI устанавливается кодом; его отдельная конфигурация, если потребуется,
живёт в собственном `modules/nwg-displays/`.

## 8. Конфиги из отдельных Git-репозиториев

Neovim получает обычный рабочий Git-репозиторий:

```text
~/.config/nvim
  → ~/.local/share/dotfiles/repos/nvim/
      ├── .git/
      ├── init.lua
      └── lua/
```

Модуль Neovim в одном месте описывает пакет, необходимые инструменты,
репозиторий `https://github.com/stounfo/nvim.git`, нужную ветку и путь подключения.
Для push можно использовать `git@github.com:stounfo/nvim.git`, сохранив HTTPS
для fetch, чтобы первоначальная загрузка не зависела от SSH-ключей.

Общий небольшой механизм внешних репозиториев получает эти объявления из
модулей. Они же используются первоначальной подготовкой и `dotfiles update`;
в CLI нет второго вручную написанного списка URL.

Поведение механизма:

1. При первом подключении клонировать репозиторий в `reposDir`, затем выставить
   ссылку Home Manager. Подготовка выполняется от пользователя до подключения
   файлов, после проверок конфликтов, вне Nix build.
2. При повторном `apply` использовать существующий репозиторий без pull,
   переключения ветки или перезаписи изменений.
3. `dotfiles update nvim` проверяет состояние репозитория и выполняет
   обновление `git pull --ff-only`. При локальных изменениях или расхождении
   веток сообщает причину остановки, не делает reset, stash или автоматический
   merge. Сборка системы для обновления не запускается.
4. При удалении Neovim из машины снять ссылку и убрать его установку из
   конфигурации. Сам рабочий репозиторий с коммитами и изменениями сохранить.

Из `~/.config/nvim` можно редактировать, делать commit и push обычным Git.
Обновления плагинов и записываемые Neovim lock-файлы остаются ответственностью
этого репозитория. Его версия не фиксируется автоматически в `flake.lock`.

## 9. Удаление и владение файлами

Отключение означает удаление программы из описания машины и успешное применение.
Ручное удаление исполняемого файла не меняет декларацию и будет исправлено
следующим применением.

| Объект | Что происходит при отключении |
| --- | --- |
| Пакет Nix из конфигурации | Убирается из текущего управляемого окружения |
| Системная интеграция | Убирается из конфигурации; для части изменений нужен перезапуск или reboot |
| Управляемая ссылка на конфиг | Снимается |
| Исходник в dotfiles | Сохраняется |
| Внешний рабочий Git-репозиторий | Сохраняется |
| Пользовательские данные и история | Сохраняются |
| Пакет из ручного `nix profile install` | Сохраняется в личном профиле |
| Приложение, скачанное и установленное вручную | Сохраняется; автоматически под управление не принимается |

Home Manager уже сопоставляет поколения и удаляет больше не нужные управляемые
ссылки. Если на их месте появился чужой обычный файл, его нельзя молча удалять.
Поведение проверки конфликтов и очистки видно в
[реализации файлов Home Manager](https://github.com/nix-community/home-manager/blob/master/modules/files.nix).
Копирование конфигов произвольными activation-скриптами этого жизненного цикла
не обеспечивает и не используется как основной механизм.

Пакет ещё может быть в старом поколении, зависимости другого пакета или
системной поставке macOS. Отключение не обещает физически стереть все копии
программы с диска. Очистка старых поколений и Nix store — отдельная операция.

При первом переходе существующие файлы явно принимаются под управление:
их содержимое переносится в выбранный исходник, а оригинал сохраняется
в резервной копии. Обычный `apply` не использует глобальный `force` для
перезаписи конфликтов. Такое принятие касается конкретных путей, а не всей
домашней директории.

### Ручные установки

Для программы, ещё не описанной в dotfiles, допустимы два способа установки:

- скачать приложение из интернета и установить его вручную;
- выполнить `nix profile install nixpkgs#package_name` в личный профиль.

`dotfiles apply` не очищает личный Nix-профиль и не удаляет приложения только
потому, что их нет в списке `modules`. Он также не забирает их конфиги под
управление автоматически. Ручные установки можно постепенно переносить в код.

Для переноса Nix-пакета добавляется модуль и применяется конфигурация, затем
удаляется именно ручная запись из профиля. Поддерживается адресное удаление
через [`nix profile remove`](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-profile-remove).
Обычный `apply` эту операцию не выполняет. Пока установлены обе версии,
фактически запускаемая определяется `PATH`; после переноса нужно проверить
путь к исполняемому файлу. Отключение модуля не удалит оставшуюся ручную копию.

При переносе скачанного приложения учитывается существующая установка,
особенно если новый пакет использует тот же путь `.app`. Конфликт разрешается
как отдельный шаг миграции с сохранением данных, без автоматического `force`
в обычном применении.

### Homebrew как внутренний способ установки

Если Homebrew нужен выбранным модулям macOS, его пакеты полностью управляются
конфигурацией. Ручных установок через Homebrew в этой модели нет. Поэтому
отдельный журнал владения casks и собственный алгоритм их удаления не нужны.

Для обычного применения используется штатная настройка nix-darwin:

```nix
{
  homebrew.onActivation = {
    autoUpdate = false;
    upgrade = false;
    cleanup = "uninstall";
  };
}
```

После удаления модуля из конфигурации Homebrew убирает больше не объявленные
пакеты. Режим `zap` не используется. Очистка относится к установкам,
зарегистрированным в Homebrew; личный Nix-профиль и независимые скачанные
приложения в неё не входят. Семантика описана в
[опциях nix-darwin](https://nix-darwin.github.io/nix-darwin/manual/#opt-homebrew.onActivation.cleanup).

На машине с уже установленным Homebrew перед первым включением очистки
нужно сверить его содержимое с новым описанием машины и перенести нужное
в модули. После этого источник состава один — конфигурация. При удалении
последнего cask интеграция Homebrew должна ещё применить пустой список,
чтобы завершить удаление.

Обновление выполняет `dotfiles update`, вызывая необходимые менеджеры пакетов
внутри себя. Пользователь работает с модулями и общим CLI; знать команды
Homebrew для установки, обновления или удаления программ не требуется.

## 10. Единый CLI и первоначальная настройка

Целевой вход для уже подготовленной ОС с Nix:

```sh
nix run github:stounfo/dotfiles#bootstrap -- personal-mac
```

Будущее приложение `bootstrap` создаёт рабочую копию в `~/dotfiles`, выбирает
описание машины и вызывает тот же механизм, что `dotfiles apply`. Если копия
уже существует, использует её без reset или незапрошенного pull.
Удалённый flake служит запуску bootstrap; редактируемые конфиги подключаются
из постоянной локальной копии. Доступ к приватному репозиторию, если он
понадобится, входит в предварительную подготовку.

Первоначальная установка Nix, ОС, Homebrew при необходимости и аппаратная
подготовка NixOS сейчас за рамками. Наличие Homebrew не должно требовать от
пользователя ручного управления его пакетами. На NixOS также должен существовать
корректный конфиг оборудования;
одна команда не угадывает разметку дисков. При первом запуске на macOS bootstrap
получает `darwin-rebuild` из закреплённого input nix-darwin: предварительно
применённая конфигурация Darwin ему не нужна. После настройки CLI устанавливается
для дальнейшей работы.

После подготовки:

| Команда | Назначение |
| --- | --- |
| `dotfiles apply personal-mac` | Применить явно выбранную машину |
| `dotfiles apply` | Применить ранее выбранную машину |
| `dotfiles update` | Обновить Nix inputs, применить конфигурацию и обновить приложения, управляемые через Homebrew, если он используется |
| `dotfiles update nvim` | Обновить только внешний конфиг Neovim |
| `dotfiles status` | Показать выбранную машину, изменения Git и незавершённые операции |

Выбранная машина и результат последнего применения хранятся в
`~/.local/state/dotfiles/`. Желаемый состав программ берётся из Nix;
отдельного реестра установленных пакетов CLI не ведёт. Для внешних репозиториев
он получает пути и команды из объявлений модулей текущей конфигурации.
Общее обновление не меняет личный Nix-профиль, скачанные вручную приложения
или рабочий репозиторий Neovim; у них самостоятельный цикл обновления.

CLI проверяет совпадение ОС и архитектуры с описанием машины, затем использует
`nixos-rebuild switch` или `darwin-rebuild switch` с выбранным flake output.
Home Manager применяется в составе системы. Репозитории, файлы и Git-операции
обрабатываются от обычного пользователя; системные права запрашиваются для
действий, которым они нужны. `apply` не делает commit/push и не обновляет
зависимости без запроса.

Исходником сборки является локальная рабочая копия. Новые Nix-файлы нужно
добавлять в Git, чтобы flake видел их; коммит перед каждым применением
не требуется. Правила локальных Git-flakes описаны в
[руководстве Nix](https://nix.dev/manual/nix/2.35/command-ref/new-cli/nix3-flake).
Для apply используется обычный локальный Git-flake без общего требования
`--impure`. Текущую зависимость Asahi от `/boot/vendorfw` нужно отдельно
разобрать при переносе аппаратного модуля.

Применение Nix, Home Manager и Homebrew не является общей атомарной транзакцией.
CLI проверяет конфликты заранее и завершает работу с ошибкой, если какая-то
часть не применилась, сохраняя сведения для повторного запуска. Успех только
системной сборки ещё не означает успешной настройки всей машины.

## 11. Воспроизводимость и секреты

Полное описание машины кодом здесь означает, что её можно собрать из описания
хоста, файлов dotfiles и объявленных внешних репозиториев. Изменения, сделанные
GUI или ИИ, становятся частью этого описания через обычный commit в нужном Git.
Незакоммиченные или неотправленные изменения не появятся на новом компьютере.
Ручные установки остаются временным дополнением вне этого описания и сами
на новой машине не восстанавливаются. Для воспроизводимого набора их нужно
перенести в модули.

Границы восстановления различаются:

- `flake.lock` фиксирует Nix inputs; поколения позволяют возвращать пакеты
  и системную конфигурацию.
- Определения собственных пакетов, их версии и хеши хранятся в Git вместе
  с модулями; они тоже участвуют в сборке Nix и откате поколений.
- Редактируемые конфиги восстанавливаются через Git. Откат поколения Nix
  оставляет содержимое рабочей копии текущим.
- Внешний конфиг Neovim имеет свою историю и свои коммиты.
- Homebrew-приложения не получают точного отката версии из `flake.lock`.

Это осознанный выбор в пользу обычного редактирования и GUI. Требовать
одновременно изменяемые на месте файлы и их неизменность в поколении нельзя.
Согласованный откат при необходимости возвращает и Nix-поколение, и нужные
коммиты конфигов.

Конкретное хранилище секретов сейчас не выбирается. В дальнейшем модуль
программы сможет принимать путь к файлу секрета, создаваемому общим механизмом
при активации. Секреты не подставляются в публичные шаблоны или Nix store;
ключи, токены и runtime-файлы не попадают в `modules/*/files/`.
Это не требует изменения способа выбора программ или разделения их модулей.

## 12. Переход от текущей реализации

1. Ввести описания `personal-mac`, `personal-nixos` и `make-host`, сохранив
   существующие аппаратные настройки и `stateVersion`. Использовать один
   список `modules` у каждого хоста. Разместить общую поддержку Apple Silicon
   в `modules/apple-silicon-support/`.
2. Сделать `default.nix` каждого переиспользуемого модуля единственной системной
   точкой входа.
   Перенести подключения пользовательских частей внутрь программы; удалить
   второй список в `home/default.nix` и отдельные импорты SSH/Hyprland из flake.
3. Перенести обычные конфиги из `old/roles` в `modules/*/files/`, проверить их
   зависимости и добавить редактируемые ссылки. Не переносить Ansible-шаги
   удаления старого конфига буквально.
4. Выделить варианты Git и каталоги Hyprland для машин. Проверить редактирование
   через используемый редактор и выбранный GUI.
5. Перенести существующий клон Neovim в постоянный каталог, сохранив `.git`,
   ветки и незакоммиченные изменения; подключить его через управляемую ссылку.
6. Добавить CLI и подготовку внешних репозиториев. Если потребуется Homebrew,
   подключить его штатное управление через nix-darwin, предварительно сверив
   существующие установки. После этого отдельно довести bootstrap до одной команды.

Критерии готовности реализации:

- Git, SSH и Apple Silicon Support выбираются через один список `modules`
  и подключаются одинаково, независимо от наличия пользовательской части.
- Одна запись в `modules` включает всю программу; её удаление убирает установку,
  интеграцию и подключённые конфиги без потери исходников и данных.
- Пакет из nixpkgs и собственный `package.nix` подключаются через один и тот же
  интерфейс модуля; определение своего пакета хранится рядом с его настройками.
- Новая машина добавляется своим описанием и аппаратными файлами без копирования
  настроек приложений. Конфигурации проверяются на обеих архитектурах NixOS
  и на macOS; сборка чужой платформы требует соответствующего builder.
- Повторный `apply` сохраняет изменения обычных конфигов, GUI и Neovim и
  не выполняет скрытых обновлений.
- Правка мониторов через GUI меняет файл только текущей машины и сохраняется
  после применения и перезапуска сессии.
- Рабочий и личный Git используют правильные данные без двух источников истины.
- Применение, обновление и отключение модулей не очищают ручной Nix-профиль
  и не удаляют независимые приложения, скачанные пользователем.
- Homebrew, если используется, управляется через конфигурацию и общий CLI;
  отдельного журнала владения пакетами нет.
- В документе реализации и CLI видна разница между откатом пакетов и конфигов.
